# Phase 10: 迭代修订 & 版本管理

本阶段是质量控制的最后一环。当 Phase 8 审查出问题，或者用户对生成的内容不满意时，进入此阶段。在此阶段，AI 需要精准地“动手术”，而不是简单粗暴地重写整章。

## 修订原则

1. **最小干预原则 (Incremental Revision)**：能改一段就不要改一节，能改一节就不要改一章。保留那些优秀的、没问题的部分。
2. **靶向治疗**：针对审查报告中明确指出的具体问题进行修复。
3. **保持衔接**：修改某个段落后，必须检查修改后的段落与上下文的逻辑和情感衔接是否依然流畅。

---

## 三种修订模式

根据问题的严重程度和用户的指令，选择合适的修订模式：

### 模式 1：局部打补丁（推荐，最常用）
**适用场景**：违背了某条设定、角色说了一句不符合性格的话、忘了一个小伏笔。
**操作流程**：
1. 定位到具体的 Markdown 行数或段落。
2. 仅重写该段落，使其符合逻辑。
3. 确保前后文的连贯性。

### 模式 2：对抗编辑 / 瘦身与强化 (Adversarial Editing)
**适用场景**：章节整体没大毛病，但是“水字数”严重，或者高潮部分不够爽。
**操作流程**：
此模式需要分为两步进行：
1. **生成修改建议图 (Cut/Strengthen Map)**：
   - 【削减建议】：标出哪些段落是无意义的内心戏、重复的环境描写，建议删除或压缩。
   - 【强化建议】：标出哪些关键动作戏不够详细，情绪渲染不到位，建议扩写。
2. **执行编辑**：用户同意建议图后，执行这些削减和强化操作。

### 模式 3：全章重构 (Full Rewrite)
**适用场景**：偏离了细纲方向、出现了 3 个以上的 🔴 致命逻辑问题、或者用户彻底否定了当前版本。
**操作流程**：
1. 让用户明确指出不满意的地方和期望的走向。
2. （如果需要）先退回 Phase 6 修改《章节细纲》。
3. 丢弃当前版本的正文，重新生成全新的章节。

---

## 版本管理规范

为了防止“越改越糟”，我们需要保留历史版本。

- 当进行【模式 3：全章重构】或发生重大修改时，不要直接覆盖原文件。
- 将原文件重命名为 `chapter-XXX_v1.md`。
- 将新版本保存为 `chapter-XXX_v2.md`（最终确定的版本可以命名为 `chapter-XXX.md`）。
- 在文档头部可以添加 Markdown 注释，简述此版本的修改原因：
  `<!-- v2 修订：修复了主角越级使用法术的设定 Bug，加强了反派死亡时的爽感 -->`

## 交互流程示例

**审查员 (Phase 8)**: “发现 🔴 致命问题：主角在此处使用了飞行能力，但 rules.md 规定金丹期以下禁空。”

**用户**: “修复这个问题，让他改用壁虎游墙功爬上去。”

**文学渲染师 (Phase 10)**:
“✍️ 收到。定位到第 15 段。
原句：‘他纵身一跃，身形在空中化作一道流光，直冲崖顶。’
**修订为**：‘他十指紧扣岩缝，真气运转间，宛如一只灵巧的壁虎，贴着陡峭的绝壁急速攀升。’
段落已更新，上下文衔接正常。请问是否还有其他需要修改的地方？”

**用户**: “可以了，提交吧。”

→ 此时流程结束，自动进入 Phase 8 重新审查。

---

## 阶段流转条件

**进入条件**: Phase 8 审查发现问题 / 用户主动要求修改（`/novel-revise [N]`）
**退出条件**:
- [ ] 所有 🔴致命 问题已修复
- [ ] 所有 🟠严重 问题已修复或用户确认保留
- [ ] 修订后的正文已替换原文件

**流转到**: **Phase 8 - 质量审查**（修订后必须重新过审，不可跳过！）

> ⚠️ 注意：修订后不是直接进入 Phase 9，而是必须重新经过 Phase 8 的完整审查。只有重审通过后，才能进入 Phase 9 状态落盘。
