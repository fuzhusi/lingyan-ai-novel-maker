## 第一部分:产品经理审查

### 产品总评

这是一台为"不懂写作的人"造的精密写作机器,但它把赚钱闭环里最难的三件事——找书、控成本、上架收钱——全部留给了用户自己。工程密度(门禁/盲审/一致性链/困惑度雷达)远超零基础新人的理解能力,而用户真正需要的临门一脚(发布对接、合规护栏、成本透明、多本管理)一件没做。当前形态是一套优秀的开发者自用研究系统,还不是能兑现"月入三五千"承诺的生产工具;而"拆书复刻"这个核心卖点,产品层面竟无一句合规警示。

### 七维度结论

1. **价值闭环断在最后一公里**:方法论四步中"拆书→微创新→生成→去AI化"全覆盖且工业化程度高,但终点是导出 TXT——无平台发布对接、无字数/更新节奏管理、无多本管理、无收入反馈闭环。用户旅程是"想赚钱→…→得到一个 TXT 文件→?(全靠教程补)"。
2. **新手体验首屏即断裂**:网关页主推"长篇/短篇创作",与方法论"新人应从拆书复刻开始"矛盾;引导卡只提供示例数据**不检测模型配置**——第一次价值体验卡在配 API key,引导对此只字未提;写作页十几个专业按钮零解释。
3. **工作流**:拆书链路是全产品最顺的一段;但"复刻为长篇+生成正文"关页即断、无 checkpoint;批量生产无任务队列/多任务视图;微创新方向可选项——新人跳过即可一键采纳出近似原书的书。
4. **信任与成本黑箱**:全系统无 token 用量/成本统计;人味分无通过线无行动指引(阈值自己都未校准);条目操作全是 alert+整页 reload,与"逐条审阅"流程自相矛盾。
5. **合规零防护**:路由名 `/plagiarize/`、遗留标签"改写洗稿"、零版权警示。判断:可管理但当前处于致命级。
6. **竞争力**:真壁垒=拆书工业化管线(云竞品因合规不敢做)+去AI化语料背书+成本结构;自嗨清单=未校准的困惑度雷达、Three.js 氛围层、16 Agent 细粒度配置、33 MCP 工具(对新人维护负担)。
7. **增长与留存**:备份只有 CLI;无日更目标/连载日历/作品看板等留存钩子。

### 致命(不修不能上)

| # | 问题 | 建议 |
|---|------|------|
| C1 | 价值闭环断在导出,无发布/投稿/变现支持 | 做"番茄短篇投稿包":按平台规范切章导出+发布前自检报告(人味分+专名差异率+敏感词) |
| C2 | 合规零警示 + "/plagiarize/"式命名 | 采纳环节加差异化门槛(微创新为空阻止"全部采纳"或强提醒);一次性合规须知;UI 文案统一为"对标拆解·差异化创作" |

### 重要(上线一个月内)

I1 成本黑箱→采集 usage 落库+进度流显示调用数;I2 人味分无解读→分档文案(<60 必收敛/60-75 可投/>75 良好)+下一步按钮;I3 复刻生成无断点→逐章落进度标记可续跑;I4 条目操作 alert+reload 循环→toast+局部更新;I5 备份只有 CLI→设置页一键备份;I6 多本管理→Novel 加 status/platform 字段变看板。

### 快赢清单(各 1-2 天)

1. 网关加拆书复刻主入口卡 + 配置检测引导(改动最小、首跑提升最大)
2. 拆书/复刻进度流加调用计数与预估(复用现有 yield 流)
3. "全部采纳"差异化门槛(微创新为空时强确认)
4. 人味分分档文案(零后端改动)
5. 合规提示条 + UI 文案去"复刻/洗稿"化

### 战略押注

1. **变现最后一公里**(投稿包+发布前自检)——从"写作工具"变"赚钱工具"的唯一路径,云竞品不敢跟进的差异化深水区;
2. **题材配方库**(4书×4要素组合,roadmap V2 项)——用户拆得越多配方越值钱,数据壁垒+留存;
3. **多本连载看板**——"云工具存你的稿子,灵砚存你的生意"的单机差异化叙事。

## 第二部分:技术总监审查

### 技术总评

当前架构能承载"一个熟练用户、单机、串行地工业化月产数本书"的上限是存在的,但每一次长管线运行都在赌网络赌进程不死赌用户不关标签页——这不是工程化生产,是把分钟级任务寄生在 HTTP 请求生命周期里的个人工具。三个硬瓶颈:①长任务无队列无恢复;②LLM 层零重试零计量;③数据完整性靠手工枚举+吞错迁移。**签字意见:不予签字上生产(当前状态);修复 P0 六项(约 2 周)并建立最低可观测性后,可签"单用户单机工业化写作工具"。**

### P1(真实使用中频繁咬人)

- **P1-1 prompt injection**:拆书输入(任意爬来的文本)直进 LLM,产物可写入"永不压缩"的 author_intent 驻留全书每一章;DOCX/EPUB 解压比无校验(50MB zip 可膨胀数十 GB)。
- **P1-2 上下文注入层 9 段 try/except-pass**:一致性保障体系自身挂了用户零感知(code-review P1-3 点名未修)。至少 logger.warning + SSE 回传 degraded 列表亮黄条。
- **P1-3 FTS 只增不更 + 单字 OR 弱召回**:审批/CRUD 不增量索引;中文逐字 OR 检索 precision 崩坏还只取前 5 条。
- **P1-4 零 token 计量零调用日志**(与产品侧成本黑箱同题):llm.py 单点采集写 llm_calls 表+dashboard 聚合;prompt 硬编码集中+版本化。
- **P1-5 三进程共库**(Web/MCP/CLI)无写重试封装:5 秒 busy_timeout 后直接抛 locked。
- **P1-6 工程质量**:Python 3.14+langchain 1.0 bleeding-edge;CI 仅 pytest 一个 job(无 lint/type/coverage);测试数量口径差;工作区未提交改动需收敛。

### P2 技术债择要

routes/pipeline.py 死蓝图仍注册;Query.get() 弃用遍处;JSON-in-TEXT 列(O(n²) 写放大,迁移 PG 时转 JSONB+拆行表);字符串状态机无 CHECK;文档口径漂移(MCP 工具数三个版本)。

### 技术债 TOP5(按 3 个月内咬人排序)

1. LLM 层无重试/计量(第一次 429 就咬,还不知道花了多少钱)
2. 长任务无队列无恢复(2 小时拆书遇重启=卡死+409 锁死)
3. FK 未启用+吞错迁移(rowid 复用把上一本书的伏笔串进新书)
4. 状态机竞窗(双标签页是自然用法)
5. "修了没锁"的流程问题(debug=True 回归事件本身)

### 架构演进路线

- **现在就做(0-1 个月)**:P0 六项(约 2 周);进程内任务执行器(**不需要 Redis/Celery**——单用户单机,DB 就是最好的队列);dev server 换 waitress。
- **触发条件 A → 换 PostgreSQL**:多用户/多写进程常态化;单库 >1-2GB;需要 JSONB/真级联。**不要为"工业化"过早换库——瓶颈在任务模型不在存储。**
- **触发条件 B → 前后端分离**:"多用户协作/移动 App"立项时;先固化 SSE 进度协议与任务 API。
- **拆分线**:llm.py+config_utils(LLM 网关)、book_deconstruct+chapter_runner+writer_chain(任务编排)两条线;**当前拆服务是负收益**。
- **工程投资 TOP3**:LLM 网关工程化(3-4 天)> 任务执行与状态机(1 周)> 数据完整性纪律(3-4 天)。
