## 1. 问题定义:落库是"交施工图",不是"倒卡片"

### 1.1 我们的场景

灵砚的拆书复刻链路:对标书 → 六维拆解(开篇节奏/金手指/架构/人物/世界观/文风)→ 待确认条目 → 采纳落库(写入角色库/世界观/大纲树)→ 章节流水线生成。

**当前痛点**:落库只搬静态卡片,丢掉了原书结构里最值钱的**时间轴信息**——人物在第几章出场、第几章退场,伏笔在第几章埋、第几章收。没有这些,生成的书知道"有谁",但不知道"谁该什么时候出现、什么时候退场";知道"有伏笔",但不知道"第几章埋、第几章必须收"。

### 1.2 四层知识模型(调研收敛出的概念框架)

所有成熟项目不约而同把叙事知识分成四层,生命周期和查询方式完全不同:

| 层 | 内容 | 生命周期 | 我们的对应物 |
|---|---|---|---|
| **L1 静态设定** | 人物性格骨架、世界观规则、文风 | 全书不变 | Character / WorldSetting / 文风锚例 |
| **L2 时序事实** | "第5-11章受伤,第12章痊愈"、境界突破、持有物变更 | 带章节区间 | 时序真相库(部分)、Character.status_json(待建设) |
| **L3 承诺/伏笔** | 埋下的钩子、许诺的回收、信息揭示计划 | 状态机流转 | Foreshadowing 状态机(已有,缺双锚点) |
| **L4 生命周期** | 出场/活跃/退场/retired | 单向(可恢复) | 无(待建设) |

**落库 = 把拆解产物按这四层分类,各归各位,并挂上时间轴锚点。**

## 2. 项目详述

### 2.1 jarvis-write —— 时序故事圣经(与灵砚最同构,工程化最深)

仓库:`https://github.com/ynnyh/jarvis-write`(Python/FastAPI + SQLAlchemy)。自述:"temporal story bible, foreshadowing scheduler, cascading outline engine"。核心文件:`backend/app/db/models/story_bible.py`、`consistency/foreshadow_agenda.py`、`consistency/reader_knowledge.py`、`fact_ledger.py`、`prompts/cascade.py`。

#### 2.1.1 数据模型(6 张表)

**Entity(实体节点)**——角色/地点/物品/势力四类:

| 字段 | 说明 |
|---|---|
| entity_type | character / location / item / faction(带索引) |
| name + aliases(JSON) | 主名 + 别名表——防 LLM 换称呼认不出同一实体 |
| base_profile(JSON) | 静态基础档案(不随章节变的不变量) |
| **retired(Boolean)** | **退场标记**:True 后生成注入不再含该实体及其事实;历史正文与事实全保留,可随时恢复 |

**Fact(时序事实)**——核心中的核心:

| 字段 | 说明 |
|---|---|
| entity_id | 事实挂在实体上 |
| fact_type | state / ability / possession / relationship / location |
| content | 事实描述 |
| **valid_from / valid_until** | **生效章节区间;valid_until = null 表示开区间(仍然生效)** |
| importance | critical / major / minor(prompt 超限时按此截断) |
| source_chapter | 证据锚:哪一章抽取出来的 |

模型注释里的范例:*"角色A第5章受伤 → Fact(valid_from=5, valid_until=11);第12章痊愈 → 新 Fact(valid_from=12, valid_until=None)。查第8章 → 命中'受伤'。"*

**Relationship(时序关系边)**:from/to 实体 + relation 短标签(20字截断,完整描述留在 facts 行——*"边上只留标签,账本才有真相"*）+ valid_from/valid_until + evidence_fact_id(指向同章双写的 fact 行,从边直达原文)+ status(pending|confirmed——抽取写的新边是 pending,不注入,等作者对账确认)。

**KnowledgeState(谁知道什么)**:fact_id + knower("reader" 或角色 entity_id)+ known_from_chapter + knower_state(known|suspected|blind)。悬疑必备:读者已知 ≠ 角色已知,生成时据此控制"角色不该说出他还不知道的事"。

**FactUsage(事实消费日志)**:一行 = (fact_id, 消费章, source, times, evidence)。source 三档可信度:`manual(人工) > retrieval(检索注入,模型确实看到) > extract(正文里字面命中,弱信号,探针短语≥4字且≥34%内容长度)`。价值:*"一条事实作废 → 哪些章要复核"从 O(章数×事实数) 全文扫描变成一次索引查询*。

**Foreshadowing(伏笔)**:四态 `planted → reinforced → paid_off / abandoned`,字段:`chapter_planted / expected_payoff_chapter / earliest_payoff_chapter(作者硬下限,不能提前收) / payoff_chapter / reinforcement_chapters(JSON数组) / importance / required_hints`。

#### 2.1.2 写回模式(拆书/抽取落库的标准动作)

```python
# apply_extraction:状态变化 = 关旧区间 + 开新区间
if replaces:
    old = self._find_replaced_fact(entity.id, replaces)
    if old:
        old.valid_until = chapter_number - 1   # 旧事实收口
fact = Fact(..., valid_from=chapter_number, valid_until=None, source_chapter=chapter_number)
```

`replaces` 的匹配做**三级模糊**(精确 → 去空白精确 → 唯一子串且≥4字,歧义不猜)——因为模型抄原文常有细微出入。关系边同理:新关系出现 → 旧边收口;相同 relation 的有效边已存在 → 幂等跳过,*"模型换措辞重述同一关系也不会抖动"*。

#### 2.1.3 角色生命周期(三层表达)

1. **区间事实**:状态变化 = 关旧开新(见上);
2. **retired 布尔**:作者手动退场,一次性表达"以后永远不在场",与区间事实正交;
3. **关系边时序**:关系演化也是关旧开新。

**退场 = 注入侧黑名单而非删除**:`retired_entity_ids()` 在硬约束块、资源账本、读者认知集三处共用同一排除口径——历史可查(回忆/复盘素材仍在),生成侧永久沉默,恢复只需翻回 False。

#### 2.1.4 查询模式:"第 N 章谁在场、什么状态"

```python
# query_facts_at(n)
q = db.query(Fact).filter(
    Fact.valid_from <= n
).filter(
    (Fact.valid_until.is_(None)) | (Fact.valid_until >= n)
)
```

- `hard_constraints_block(n, 出场名单)`:渲染 prompt 硬约束块——涉及角色的**当前**状态事实 + **仅双方都在出场名单内**的有效关系边;retired 实体一律不注入;单章最多 40 行,超限按 critical>major>minor 截断。
- `known_roster_block()`:**已登场角色名册**,防"凭空冒出常驻角色"。
- 实体解析一次全载建 name+alias 索引(实体量有界),避免逐名 N+1。

#### 2.1.5 伏笔日程编排(治"模型爱埋不爱收",全部零 LLM)

`foreshadow_agenda.py` 三件套:

- **准入控制**:活跃伏笔上限 = `max(2, 目标章数 // 20 * 3)`;超容时 prompt 里是**禁令**:"本章不要再埋新伏笔,先把欠着的收回来"。
- **排程**:`must_payoff`(本章必须兑现,≤2条/章,防"清账章";排序 = 逾期最久优先 + 重要度)/ `should_reinforce`(≤3条)/ `still_pending`(明确告知"欠着账,别当成不存在")。注入块标题是"排程算出来的硬性任务,不是可选提醒"。附写作指导:"收伏笔要比埋伏笔好看:把揭晓放在一次冲突、一个动作、或一句没说完的话里"。
- **债务审计**:`{active, overdue, serious(逾期>5章), avg_hanging, longest_hanging}` 供健康报告。

章后回写:LLM 抽取 `foreshadow_ops`(plant/reinforce/payoff),**reinforce/payoff 必须逐字抄已登记伏笔原文**,三级模糊匹配(精确→去空白→唯一子串≥8字),多条命中视为歧义"宁可漏配不误配"。`purge_chapter_ops` 支持**重写撤销**:该章埋的删、该章收的回退为 reinforced/planted、强化记录摘除该章。

#### 2.1.6 计划-实际一致性

- **FactUsage 失效传播**:`invalidate_fact` 把 valid_until 拨前,反查消费章产出"受影响章节清单"交给级联引擎;**只产报告不执行**。
- **大纲级联**(`cascade.py`):改动先 LLM 分级 major/minor;major 才做影响分析(下游最多 30 章 + 未回收伏笔最多 40 条作输入,产出 `action: regenerate|review`,只认喂过的章号白名单);重生成提示词带硬规则:**"最小侵入,能保留的尽量保留;伏笔链保持完整:上游改动若取消了某伏笔,本章不得再回收它"**。级联永远不自动执行,用户拍板。
- **交稿对账**(`reconciliation.py`):每章后把"系统自动建联"摆给作者——pending 关系边(带证据引文)/梗兑现账/伏笔变动;作者 reject 的边删除并**收口其证据事实**(更早章 valid_until=n-1,本章直接删,KnowledgeState 引用一并清)。
- **核心梗账本**(`premise_ledger.py`):高概念+兑现机制+3-6 拍节拍表+钩子计划;每章抽取时判 `premise_check{fulfilled, beat 照抄节拍表, strength1-5, evidence}` 落账,**连续 False 是文扑前兆,体检标红**——"计划(节拍表) vs 实际(逐章记账)"的最小实现。

#### 2.1.7 读者认知集(揭示调度的运行时视图)

`reader_knowledge.py`:*"反转写不好,是因为模型不知道要掀翻什么"*。从 KnowledgeState 派生读者认知地图:known(已披露)/ held(压着的底牌,critical/major 且 valid_from<n)/ asymmetries(角色知道而读者不知道的信息差)。转折章判定后注入**反转预备块**:"写反转的第一原则:不要靠人物开口解释真相"。另做**披露节奏审计**:连续多章零披露 → 读者疲劳;一章爆一堆 → 填鸭(advisory 不阻断——*"先 advisory,看数据质量再硬化"*)。

#### 2.1.8 可借鉴点清单

1. 事实区间模型(开区间 + 关区间,null=仍有效)= 我们 Foreshadowing 状态机在"角色状态"上的对偶;
2. FactUsage 消费日志做反向影响索引;
3. 抽取新边 pending / 作者确认 confirmed 的两段式信任流;
4. retired = 注入侧黑名单(历史可查、生成沉默、可恢复);
5. 伏笔双锚点(earliest 不可提前 + expected 预期)+ 准入上限 + 每章回收配额 + 债务审计;
6. 排程结果是"硬性任务"注入,不是可选提醒;
7. 兑现判据"逐字抄原文 + 模糊匹配 + 歧义不猜"。

### 2.2 ProseForge —— 承诺台账三节点闭环(计划-核对-登记的完整流水线)

仓库:`https://github.com/remacheybn408-boop/ProseForge`(SQLite 记忆、21 道 Guard 门禁、Agent 陪审团)。核心文件:`domain/story_bible/entities.py`、`application/story_bible/promise_tracker.py`、`application/agents/promise_handlers.py`。

#### 2.2.1 承诺建模:统一圣经表 + 严格迁移表

所有设定统一为 `StoryFact(kind, key, value_json, status, confidence, source, pinned, version)`,promise 是其中一种 kind:

```python
PROMISE_STATES = frozenset({"open", "developing", "resolved", "abandoned"})
PROMISE_TRANSITIONS = {
    "open": ("developing",),
    "developing": ("resolved", "abandoned"),
    "resolved": (),   # 终态不可逆
    "abandoned": (),
}
RETRIEVABLE_STATUSES = frozenset({"active", "open", "developing"})
```

**关键设计:检索层只能看到 RETRIEVABLE_STATUSES**——终态与 excluded 行永不回流场景包(*"已回收伏笔不复发"在存储层就卡死*)。埋/收锚定:埋时写 `value_json.introduced_chapter`,收时追加 `resolved_chapter`;兑现证据累计在 `value_json.fulfillments[{chapter, quote}]`。

另有 `chapter_fact`(每章事实快照)与 `character_state`(人物最新状态)两种 kind 与时序真相同构。**圣经 = 钉选的静态真相(pinned),台账 = 带生命周期的动态承诺,同表同检索口径**。

#### 2.2.2 生成内环:契约 → 核对 → 登记 三节点

- **promise_contract(章前)**:台账直查(promise+character_state 且 status∈RETRIEVABLE)+ 叙事 RAG 双路取证 → LLM 产契约卡 JSON:`due[{key, source_chapter, evidence, required_fulfillments, remaining, reason}](本章应兑现的)/ plant[{hook, note}](本章应埋的)/ watch(受伤/奖励/状态提醒)`。渲染上限 1200 字注入 writer 与 editor;**任何失败降级为空契约、不注入、链路不退化**(best-effort 全线贯彻)。
- **promise_verify(章后)**:终稿 + due 清单 → LLM 逐条判 `{key, fulfilled, quote}`,**"只在正文能找到明确对应情节时判 fulfilled=true,quote 必须出自终稿原文"**。fulfilled 则 fulfillments 累计,≥required_fulfillments 按迁移表打勾;**未兑现记 `promise_missed` 审计事件(advisory,不进门禁)——"不毙稿,但留痕"**。取证双路(RAG 定向检索 + 本章分段扫描),任一失败回落全章通读并落 fallback 事件。
- **promise_register(章后)**:LLM 提取新埋承诺(category ∈ 伏笔/钩子/承诺/受伤/奖励,confidence=0.6),与既有台账**语义判重**(duplicate_of),命中即并入既有行(version+1)不删行。

#### 2.2.3 确定性层:章目标里的"伏笔/钩子"行驱动状态机

批处理 goal 里一行 `伏笔/钩子:X`,**纯正则**解析:`埋入/铺垫/暗示` 前缀 = plant(status=open + introduced_chapter),`回收/照应` = resolve(必须走 open→developing→resolved 两跳);重复埋同一 open 承诺只推进到 developing,**幂等不重复建行**。

#### 2.2.4 档案官技法(`craft-foreshadowing/SKILL.md`)

*“管理的核心是台账,不是灵感”*——每条伏笔规划"埋—提醒—收"三步,**提醒点放在回收前约两成处**;"回收必须升级信息;定期审计超期;作废伏笔要给软处理,不能硬断线"。`promise_keeper.md` 档案官人格:"凭引文说话,无据不录;无引文即判未兑现"。

#### 2.2.5 可借鉴点清单

1. 契约卡三段式(due/plant/watch)+ **引文判据**("无引文即判未兑现");
2. 未兑现 = 审计留痕不毙稿(advisory);
3. 登记判重(duplicate_of)防台账膨胀;
4. best-effort 降级哲学(任何辅助环节失败不阻断主链路);
5. 存储层 RETRIEVABLE 白名单防"已回收伏笔复发";
6. 章目标正则驱动状态机(确定性 + LLM 双轨)。

### 2.3 chinese-novelist-skill —— 设定词典五列(读者认知时间轴的最小完备模型)

仓库:`https://github.com/PenglongHuang/chinese-novelist-skill`(~2888★,纯 Markdown/JSON,无代码库)。

#### 2.3.1 设定词典

`01-大纲.md` 内一张表,随创作持续维护:

```markdown
## 设定词典
| 名词 | 首现章节 | 读者已知 | 完整真相 | 计划揭示 |
|------|---------|---------|---------|---------|
| 蓝晶 | 第1章 | 贵重晶体,黑市硬通货 | 储存记忆的载体 | 第8章 |
```

五字段精准对应:**出场时间锚(首现章节)、信息分层(读者已知 vs 完整真相)、披露调度(计划揭示)**。规则:"新名词首次出现时必须给读者上下文线索;揭示兑现后更新「读者已知」栏"。以**读者信息量**为中心,而非伏笔对象。

#### 2.3.2 写前三查(最廉价的计划-执行校正)

每章写前硬步骤:"本章用到的名词,首现的须带线索,已介绍的表述不得超出「读者已知」栏,**到达「计划揭示」章节的必须兑现**"。配套:"每章至少回应一个旧悬念 + 提出一个新悬念 + 未解悬念清单定期检查"。

#### 2.3.3 章节规划表(在场名单的人肉版)

`| 章节 | 标题 | 核心事件 | 承接上章 | 章首引子类型 | 悬念钩子 | 出场人物 | 场景列表 |`——每章一行的**在场名单**。写前"读 00-人物档案.md 只取本章出场角色"的性格/缺陷/口癖/关系。

#### 2.3.4 可借鉴点

1. 设定词典五列 = 读者认知时间轴的最小完备模型(我们加 `first_chapter + reader_known + planned_reveal` 即可获得全部表达能力);
2. "写前三查"是零成本的流程钩子;
3. 首现管理三选一给线索:类别+特征 / 角色反应传递重要性 / 对话点出门道(*"悬念是读者知道该问什么,困惑是读者连这个词是什么都不知道"*)。

### 2.4 NovelForge —— 卡片树时间轴 + entity_list 白名单 + 卷末快照

仓库:`https://github.com/RhythmicWave/NovelForge`(FastAPI + Electron,AGPL-3.0)。核心文件:`backend/app/bootstrap/card_types.py`、`schemas/entity.py`、`schemas/foreshadow.py`、`bootstrap/prompts/`(含整套拆书提示词)。

#### 2.4.1 拆书阶段模型(与我们的需求字面对口)

```python
class BookStageItem(BaseModel):
    stage_name: str        # "穿越与萌芽"
    chapter_start: int     # 阶段起始章节号(全书序号)
    chapter_end: int
    stage_outline: str     # 必须含:起因/目标/冲突/关键事件链≥3条/角色关系能力变化/结果与下阶段钩子
    stage_summary: str     # 400~800字剧情概述
```

**每阶段硬绑 [chapter_start, chapter_end] 章节区间**——时间轴锚在阶段卡上。

#### 2.4.2 阶段衔接:上一阶段注入 + 卷末快照收束 + 主线配额

- 阶段大纲卡注入 `@type:阶段大纲[previous:global:1].{stage_name, entity_snapshot, ...}`,并强约束:"请务必在 stage_count 个阶段内将故事按分卷主线收束,并**达到卷末实体快照状态:@parent.content.entity_snapshot**"——**快照 = 实体状态的目标态(计划值)**。
- 钩子传递是提示词必填项:"悬念/钩子(**跨到下一阶段的未解问题**)"+"参与实体(仅从提供实体中选择,不得自创)"。
- **节奏分配配额**:阶段1主线仅启动、阶段3主线达成度≤50%、阶段6只做"本卷层级"收束保留长线悬念——把"主线推进量"做成分阶段配额。
- 章号强约束:`chapter_outline_list` 必须连续且完整覆盖 reference_chapter 区间。

#### 2.4.3 实体卡与在场过滤

| 卡类型 | 静态字段 | 时间/动态字段 |
|---|---|---|
| CharacterCard | name, role_type, born_scene(出场场景), personality, core_drive, character_arc, **life_span(长期/短期)** | **last_appearance[卷号,章号]**;**dynamic_info 八类动态字典**(系统/金手指/等级境界/装备/知识情报/资产/功法/心理目标) |
| SceneCard / OrganizationCard / ItemCard / ConceptCard | 各自静态 | dynamic_state / last_appearance / known_by(谁知道) |

**模板 DSL 做在场查询**——章节正文卡通过 `entity_list`(本章出场实体名单,由章节大纲生成时写入)过滤卡片:

```
角色卡:@type:角色卡[index=filter:content.name in $self.content.entity_list].{...}
上一章节大纲:@type:章节大纲[... chapter_number = $self.content.chapter_number+1].{...}   # 防剧透下一章
```

选择器语法:`[previous:N]` 最近 N 张 / `[previous:global]` 全历史 / `[index=filter:条件]` 按字段过滤。写完章节后反向抽取 `UpdateDynamicInfo` 更新角色卡(预览确认后写回)。

#### 2.4.4 可借鉴点

1. **entity_list 出场白名单**:"确保生成内容只会出场这些实体"——章节粒度的在场控制;
2. **entity_snapshot 卷末快照** = 拆书复刻时"改写版剧情收束到同样节点状态"的目标态机制;
3. **life_span + born_scene + character_arc**:角色生命周期的轻量字段组;
4. **last_appearance[卷,章] 二元组**:多卷坐标的最简表达;
5. 主线推进的阶段配额(防"前紧后松"的结构性漂移);
6. dynamic_info 八类闭集 + 写后反向抽取。

### 2.5 StoryForge —— canon 可弃缓存 + 事件溯源状态账本

仓库:`https://github.com/XZZKANY/StoryForge`(Python/FastAPI 桌面 IDE)。核心理念:*"手稿正文是唯一真值源,canon 是从正文可重建的**可弃缓存**"*。核心文件:`canon_store.py`、`tools/specs/project_canon_specs.py`。

#### 2.5.1 观察写回的三段式参数契约(拆书式批量回填的直接参照)

```
entities:        [{name, aliases[]}]
holder_claims:   [{item, holder, from_chapter, to_chapter}]     # 唯一持有区间
exit_claims:     [{entity, exits_after_chapter, reason}]        # ★退场声明

```

## 4. 关键设计决策分析(带取舍)

### 4.1 锚定方式:章节号 vs 事件 vs 阶段

- **章节号区间**(jarvis-write):查询最强(`query_facts_at`),但**拆书复刻场景有个致命问题——原书章号 ≠ 新书章号**(原书 300 章,新书按关键事件建章可能只有 60 章)。
- **关键事件锚**(我们的方案):原书"第 145 章埋伏笔"改记为"在『觉醒系统』事件埋"——关键事件就是新书的章,锚点换算是确定性查表(事件名 → 已采纳大纲条目 → 章节号)。**这是拆书场景的正确选择**;落库后换算成章节号存储,享受 jarvis 式区间查询。
- **阶段+位置**(降级):锚定的事件未被采纳时,退化为"第 X 阶段中段"并标警告。
- 多卷:单书系统用全书章号 + volume 冗余列即可;NovelForge 的 [卷,章] 二元组和 StoryForge 的四级坐标是扩展参照。

### 4.2 区间事实 vs 事件溯源

- **区间事实**(jarvis-write):查询强,适合"第 N 章状态"高频读;
- **事件溯源 + 投影**(StoryForge):审计强、投影可重建,适合"批量回填后还要重算"的场景——**拆书落库正是批量回填**。
- 灵砚的取舍:落库的计划值量不大(人物 plan + 伏笔表),直接写终态即可;但**若未来做"生成后反向回写角色动态"**,InkAI/StoryForge 的 append-only 历史模式值得跟进。

### 4.3 计划值 vs 真实值:双锚点 + 差异分类 + 顺延优先

1. **双锚点**:只有超时预警(单侧)会放行"提前泄底"——必须加 `earliest(不可提前收) + expected(预期收)` 双约束(原书的埋/收章天然给出)。
2. **衍生配额**:原书的埋/收密度就是 pacing 的量化——活跃伏笔容量上限(约每 20 章 3 条)、每章回收配额(≤2 条)是纯确定性规则。
3. **差异分类**:生成与计划不符时,minor(提前/推后一章)自动顺延计划值并留痕;major(计划回收但正文没收、或回收方式矛盾)才进重写/人工队列——与灵砚现有的抽取待确认队列天然吻合。
4. **全行业共识:不自动重写**。三个项目罕见地一致:留痕(ProseForge)或排程顺延(jarvis-write),重写永远用户拍板。
5. **兑现判据一律"引文制"**:核对输出必须带出自终稿原文的 quote,"无引文即判未兑现";状态翻转没有原文锚点是"已回收伏笔复现"误报的根本原因。
6. **计划值必须显式分层**:Creader.io 排除"未写章节的设定"——因为人类作家写的是既成事实;拆书复刻先有计划,所以计划值要带 plan 标记与事实分层,生成确认后才晋升为事实。

### 4.4 advisory vs 卡口:证据制与宁可虚报

- 确定性检查**宁可虚报也不漏报**(StoryForge 退场校验:blocking=结构矛盾,advisory=可能是回忆/同名须抽读);
- **advisory 不设卡口**——报告给人复核,不用有噪检查硬拦生成(jarvis-write:"先 advisory,看数据质量再硬化");
- 两段式信任流:自动抽取 pending,人工确认 confirmed 后才注入;
- 拆书/抽取产物**必带原文证据引文**(Maliang ≥100 字、jarvis source_chapter、StoryForge grounding——三强共识)。

### 4.5 人物生命周期:退场 = 注入侧黑名单,不是删除

- retired 布尔 + 三处检索口径统一排除 + 历史保留可恢复(回忆素材仍在库);
- 再加**已登场名册**(known_roster)对照"凭空常驻";
- 拆书落库:原书人物生命周期 = `plan_exit_chapter + exit_reason`(计划值),生成第 N 章拼 context 前先算黑名单;**正文若仍出现黑名单实体 → "死人复活"的确定性信号(名字/别名命中即可判,不需 LLM)**;
- 回忆场景用显式白名单通道(scene 标记 flashback 才放行 retired 实体),不要靠模型自觉;
- 行业现状:Sudowrite 的 Dead Character Markers 还在功能请求阶段——做成一等公民即领先。

### 4.6 上下文卫生与轻量字段

- 关系边上只挂短标签,完整描述留账本(*"边上只留标签,账本才有真相"*);
- prompt 硬约束块有行数上限(40 行)并按重要度截断;
- 别名表(aliases)是防"换称呼认不出实体"的廉价保险;
- 写前读出场的角色/设定(写前三查)是最廉价的计划-执行校正,提示词注入同构。

## 5. 对灵砚的落地映射建议

### 5.1 我们已有 vs 缺什么

| 能力 | 现状 | 调研后该补的 |
|---|---|---|
| 伏笔状态机 + 超时预警 | ✅ 已有(单侧锚) | **双锚点**(earliest/expected)、活跃容量上限、每章回收配额、债务审计、回收引文制 |
| 时序真相 | ✅ 抽取队列人工确认(pending→confirmed 两段式已有!) | 状态变化"关旧开新"的区间语义(可复用 temporal_truth 扩展) |
| 人物生命周期 | ❌ 无 | plan 字段(首现/退场/方式,按关键事件锚)+ retired_at(真实值)+ 死人复活确定性检查 |
| 出场控制 | ✅ 写作页"出场角色勾选"(手动) | 按 plan 自动预选本章出场人物 |
| 读者认知 | ❌ 无 | 伏笔表加 reveal 语义后可派生(第二期) |
| 拆书产物证据 | ❌ 无 | 条目带原书章号/摘要引文回指 |
| 计划-实际偏差 | ❌ 无 | 差异分类(minor 顺延/major 人工),接抽取队列 |

### 5.2 表结构扩展建议(具体到字段)

```
Character.status_json 增加 plan 层(零迁移):
{
  "plan": {
    "first_event": "觉醒系统", "first_chapter": 1,
    "exit_event": "宗门大比", "exit_chapter": 45,
    "exit_mode": "弧光完成", "key_chapters": [1, 12, 45]
  },
  "retired_at_chapter": null      // 真实值,生成中回填
}

Foreshadowing 增加(走 init_db migrations):
  earliest_resolve_chapter INTEGER   // 不可提前收(计划值)
  expected_resolve_chapter INTEGER   // 预期收(计划值,与现有 resolve_chapter 语义分层)
  source_event TEXT                  // 拆解锚点原值(事件名,审计回溯)
  evidence TEXT                      // 原书摘要引文(证据制)

DeconstructItem.kind 增加 "foreshadow"(伏笔条目进待确认队列,
  content_json: {title, description, planted_event, resolve_event, importance})
```

### 5.3 落库管线(锚点换算)

```
拆解(L3 增强):structure.stages 之外增产
  foreshadows[{title, description, planted_event, resolve_event, importance}]
  characters[].plan{first_event, exit_event, exit_mode}
      ↓ 待确认队列(支持 AI 改写:描述换皮,锚点事件保留)
落库(复刻为长篇):
  1. 采纳的大纲条目建章 → 建「事件名 → 章节号」映射表
  2. 人物条目 → Character(status_json.plan,事件锚查表换算章号)
  3. 伏笔条目 → Foreshadowing(planted_chapter/expected_resolve_chapter/
     earliest_resolve_chapter/evidence,事件锚换算;锚点未采纳→降级阶段+警告)
生成链路(全部复用既有机制):
  - 写作页出场角色按 plan 自动预选
  - 硬约束注入"本章 must_payoff 伏笔"(≤2 条)+ 容量禁埋令
  - 退休黑名单(dead character 检查 = 名字命中)
  - 审批抽取队列持续用真实正文校正计划值(差异分类:minor 顺延/major 人工)
```

### 5.4 分期路线

- **第一期**:L3 拆解增产伏笔候选+人物时间线(事件锚)→ kind="foreshadow" 进队列 → 落库换算 → 写作页 plan 预选 + must_payoff 注入 + retired 黑名单检查;
- **第二期**:双锚点+容量配额+债务审计的伏笔日程编排器;读者认知集运行时视图;FactUsage 式消费日志;
- **第三期**:生成后反向抽取角色动态(dynamic_info 模式);偏差报告页;级联影响分析。

## 6. 附录

### 6.1 提示词片段集(可直接借用)

**伏笔排程注入**(jarvis-write 语义):
> 以下为排程算出的**硬性任务**,不是可选提醒——【本章必须兑现】(≤2条,逾期最久优先):…;【应强化】:…;【明确欠着账,别当成不存在】:…。收伏笔要比埋伏笔好看:把揭晓放在一次冲突、一个动作、或一句没说完的话里。

**容量禁埋令**:
> 当前活跃伏笔已达上限,本章不要再埋新伏笔,先把欠着的收回来。

**退场/复活纪律**:
> 以下角色已退场:…。本章正文不得让他们以"在场"方式出现;如需回忆/闪回,须明确以回忆笔法书写。

**反转预备**(jarvis-write):
> 写反转的第一原则:不要靠人物开口解释真相。

**档案官人格**(ProseForge):
> 凭引文说话,无据不录;无引文即判未兑现。

**写前三查**(chinese-novelist-skill):
> 本章用到的名词,首现的须带线索,已介绍的表述不得超出「读者已知」栏,到达「计划揭示」章节的必须兑现。
