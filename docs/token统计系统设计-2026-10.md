# Token 统计系统设计方案（v2 评审修订版，2026-10-03）

> v1 讨论稿经两路评审（设计评审 + 红队）后修订。评审联合结论：**方向成立，两处核心假设被推翻，采纳收窄版分两步走**。

---

## 〇、评审推翻的两处核心假设（对 v1 的修正）

1. **「cfg 塞 meta 零调用点改动」不成立**。llm.py 五个入口全是散参签名（不接收 cfg），cfg 在 21 个文件 38 处解包后才进 llm.py——塞进 cfg 的 meta 会死在调用方，只写出一列全 NULL。真实选项只有：llm.py 加 meta=None kwarg + **chokepoint 补传**（推荐），或 contextvars（无先例），或 38+ 调用点全改。
2. **「stream_usage 探测降级」违反计量纪律**。stream_usage=True 是带内变更（改生成请求体），探测降级要故意让用户请求先失败一次——污染失败率统计、custom 网关按 provider 记忆必然误判（同网关不同模型支持度不同）、还得解析 400 文本区分原因。这条链正是 7062224 事故链，新形态不是"少记"而是"把生成挂了"。**流式 usage 移出第一步**，待主力厂商（GLM）cached_tokens 实测后单独评估。

另修正：Anthropic 字段名是 `input_token_details`（键 cache_read/cache_creation）；且其 input_tokens **已含**缓存部分——入库口径 `input_uncached = input_tokens − cache_read − cache_write`，否则三列相加重复计费。

## 一、真缺口（红队修正后的定位）

厂商后台已回答"花了多少钱"；真正缺的两样：
1. **按章/按 Agent 分账**——哪一章花得多、哪个 Agent（writer/converge/blind/critic）是吞金兽；
2. **缓存收益验证**——DeepSeek 命中价 0.02×，可能是账单最大变量；但 GLM 隐式缓存 cached_tokens 可能恒 0（需实测，实测前不预设价值）。

现有 `llm usage`（chars/2 粗估）+ 一条 SQL 已能答 80% 的问题；本系统补的是**精确 usage 事实 + 归因维度**。

## 二、收窄版方案（分两步）

### 第一步（0.5~1 天）：带外 usage 采集 + 归因标记
1. **非流式 usage 提取**（纯带外零风险）：`_call_llm_sync_once` 的 `llm.invoke()` 结果读 `usage_metadata`（input_tokens/output_tokens；Anthropic 再取 `input_token_details` 拆缓存），经重试链带到 `_record_llm_call`。
2. **llm_calls 加 3 列**：`input_tokens / output_tokens / cache_read_tokens`（INTEGER，NULL=厂商未报）。output 已含 reasoning，不单列（统计口径简化）。`prompt_chars/output_chars` 保留。
3. **裸 sqlite3 两条 INSERT 同步加列**（llm.py 双路径写库点，评审点名遗漏）。
4. **归因用 pipeline marker（零侵入 llm.py 签名）**：chapter_runner 流水线起止各写一行 kind="marker" 的 llm_calls（含 novel_id/chapter_number），每章成本 = 两次 marker 之间（created_at 区间）的行聚合。短篇/盲审/改稿等非 pipeline 调用归因暂用 kind+model 维度（novel_id 允许 NULL）。
5. **成本查询时计算**：CLI `llm usage` 升级用真 token（缺失回退 chars/2 并标注），成本按内置价格表（Setting 键 `model_prices`，DeepSeek/GLM 默认表）在输出侧换算，**标注价格表版本与误差性质**（GLM 缓存恒 0 → 成本系统性偏高，如实说明）。不落 cost 列。
6. **顺带修既有 bug**：cli.py:2451 的 created_at 过滤用 ISO "T" 而写入是空格格式，当天记录会漏。
7. **删死代码**：llm.py `_call_embedding`（零调用方）。

### 第二步（实测后再定）：流式 usage 采集
- 前置：在主力厂商（GLM glm-5.3-flash）实测 cached_tokens 是否恒 0、stream_options 是否支持——**实测报告决定投入**；
- 方式：ChatOpenAI 构造参数 `stream_usage=True`（pydantic 字段，非 invoke kwarg，不会透传给 API）+ chunk 级 last-wins 跟踪；Anthropic 默认带 usage 直接采；
- **1-token 探测**：首轮生成前用 1 token 请求探测端点支持度（不是拿用户真实请求失败探测），结果按 provider+model 记忆；custom 网关按 model 记忆；
- 验收标准（加严版，来自设计评审）：单次调用 token 五列之和与厂商后台同请求 usage 完全一致；失败行（ok=0）被聚合天然排除；"prompt 200+ token、输出 0 但厂商计费"的边界场景 usage 仍落库。

## 三、明确不做（评审确认）

- cost 列落库（伪精确：DeepSeek 时段价、GLM 缓存恒 0、厂商调价——token 存事实，价格查询时算）
- cfg["meta"] 穿透、contextvars、38+ 调用点全改
- 网关级硬预算/429、价格热更新、多币种、LLMLingua 联动
- tiktoken 本地精确计数（usage 缺失时维持 chars/2 兜底口径）

## 四、时间线

第一步 0.5~1 天（带外采集+3 列+marker+CLI）→ 第二步待 GLM 实测报告（0.5~1 天，含 1-token 探测）。合计 ≤2 天，比 v1 估计（2.5~3 天）省一半以上。
